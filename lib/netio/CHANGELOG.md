# Changelog of jflib-netio

What changed in this crate. All of JFLib's crates share one version and are released together;
the [library's changelog](https://github.com/JFLibrary/JFLib/blob/main/CHANGELOG.md) has the
whole picture. The format follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/),
versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html) as JFLib's
[VERSIONING.md](https://github.com/JFLibrary/JFLib/blob/main/docs/VERSIONING.md) describes.

## [Unreleased]

### Added

- WebSocket (RFC 6455, G7d): `ws::Acceptor` answers upgrade requests in a `Server`'s handler (`accept(&req, on_open)`: 101 and the connection on a thread of its own, or 400 / 403 for an origin not on `origins` / 426 / 503 past `max_connections`; subprotocols by `protocols`), `ws::connect(url, &ClientConfig)` for clients (ws://, wss:// through a connector; the server's Sec-WebSocket-Accept checked, extensions refused), `ws::WebSocket` with `recv` / `recv_timeout`, `send_text`, `send_binary`, `send_fragmented`, `ping`, `close`; pings answered, pongs taken, the close handshake both ways, a ping after `ping_ms` of quiet, the end after `idle_ms`. `ws::Decoder` reads frames of untrusted bytes without I/O within `ws::Limits` (frame, message, fragments) and names the close code of anything malformed (1002, 1007 for bad UTF-8, 1008, 1009); `ws::encode_frame`, `ws::apply_mask`, `ws::accept_key`, `ws::close_code_valid`, `ws::parse_url`. Messages and bytes a second per connection as token buckets (1008 beyond). docs/TRANSPORT.md
- `http::Body::Upgrade(http::Upgrade)`: with status 101 the server sends the head as the handler built it and hands the connection (`http::Upgraded`: the stream, the bytes read after the request, the peer, the server's stop flag) to the upgrade on a thread of its own; `Server::stop` waits for those threads, `Server::upgraded()` counts them. `http::write_switch`, `http::Reader::take_buffered`; `http::reason(101)`.

- `ssh::Client::set_time_limit(ms)`: each following `auth_password`, `auth_key` and `exec` ends with `TimedOut` after that time in all.
- `x509::NameConstraints`: `permitted_email` / `excluded_email`, `permitted_uri` / `excluded_uri`, `permitted_dn` / `excluded_dn`, `other_forms`; `x509::Cert`: `emails` (with the subject's emailAddress), `uris`, `dirs`, `other_names`
- TLS server: takes TLS_AES_128_GCM_SHA256 and P-256 (secp256r1) key shares besides ChaCha20-Poly1305 and X25519, as RFC 8446 9.1 requires of every TLS 1.3 implementation; the group is the first of the client's list that the server has (with a HelloRetryRequest for it when the client sent no share), a key share for a group the client does not list or a second share for a group is refused (illegal_parameter), and to a client that sent a legacy session id the server sends the dummy change_cipher_spec of middlebox compatibility (RFC 8446 D.4). Its certificate and signatures stay Ed25519
- TLS: `Trust::Custom(Verifier)`, a check of the peer's certificates the program brings (a PKI of its own, SPKI pinning, Certificate Transparency, the platform's verifier); a client offers with it what it offers with `Trust::System`
- TLS with the keys of the web PKI: `tls::Identity` holds an `x509::PrivateKey` (Ed25519, ECDSA P-256 / P-384, RSA); `Identity::new(chain, key)` and `Identity::from_pem(certs, key)` ("PRIVATE KEY", "EC PRIVATE KEY", "RSA PRIVATE KEY"; the key must be the leaf's). Server and client sign the handshake with ECDSA (the hash of the key's curve), RSA-PSS or Ed25519 in a scheme of the peer's list, and take server and client certificates of every kind (a client whose key signs in none of the schemes of the server's CertificateRequest sends no certificate, RFC 8446 4.4.2); `Trust::Anchors` takes CAs of any of these keys. A browser can now use a netio server with the certificate of a public CA
- TLS: TLS_AES_256_GCM_SHA384 (the key schedule with SHA-384), in TLS 1.2 ECDHE_ECDSA / ECDHE_RSA_WITH_AES_256_GCM_SHA384; the key exchange groups X25519MLKEM768 (post-quantum hybrid of draft-ietf-tls-ecdhe-mlkem; a client sends key shares for it and for X25519), SecP256r1MLKEM768, SecP384r1MLKEM1024 and P-384 on both sides (`tls::kx`); `TlsStream::group()`
- TLS: SNI on the server: `ServerConfig::identities` (certificates for other names, or of other key types for the same name) and `ServerConfig::select` (the program's own choice by `tls::Hello`: the name, the protocols, the signature schemes; certificates renewed while the server runs); the server confirms a name its certificate has (RFC 6066), `TlsStream::server_name()`. ALPN (RFC 7301) on both sides: `ClientConfig::alpn` (names of 1 to 255 bytes, 8 KiB of them at most), `ServerConfig::alpn`, `TlsStream::alpn()`, the client's names as bytes in `Hello::alpn`; a client that shares no protocol with the server gets no_application_protocol. https and wss connectors offer http/1.1 (RFC 9325, against cross-protocol attacks)
- TLS 1.3 resumption with session tickets (RFC 8446 2.2, 4.6.1): `ServerConfig::tickets` (`tls::Tickets`: stateless tickets sealed with XChaCha20-Poly1305 under keys that are made and replaced each lifetime by themselves, the previous one still taken, or `set_keys` for servers that share them; `lifetime` (a day, at most 7), `per_handshake` (2), `rotate`) sends tickets after each handshake and takes them back with psk_dhe_ke (the PSK and a fresh key exchange, no certificates); `ClientConfig::sessions` (`tls::Sessions`: a client's tickets kept per server name, trust and client identity, each used once, 8 per server) offers one; `TlsStream::resumed`, `Conn::resumed`. A session lasts at most 7 days from the handshake that authenticated it, however often its tickets are renewed. A server takes a ticket only for the same server name and suite hash and, when it asks for client certificates, one whose certificates the same trust takes again (each resumption checks the whole chain, so a client a `Trust::Custom` refuses since is not resumed); the resumed connection keeps them (`peer_certs`), and a chain over 16 KiB gets no ticket
- TLS 0-RTT (RFC 8446 2.3, 4.2.10, 8), only where the server allows it: `ServerConfig::early_data` (the most bytes of early data a ticket allows; 0, the default: none), `tls::connect_early(stream, cfg, data)` -> the stream and the bytes of `data` the server took (the caller sends the rest; nothing is resent by itself), `Conn::client_early`. The server takes early data only with the first PSK, the suite and ALPN protocol of its session, with no more than the server takes now (a ticket that allows more is resumed without it), from a ClientHello within 10 s of the ticket's age and the first time it comes (an in-memory register of 20 s, or `Tickets::replay_check` for servers that share tickets), keeps it apart (`TlsStream::read_early`, `Conn::read_early`) and hands what is not read there to `read` once the handshake is done; a server that took 0-RTT returns from `accept` after its flight and may answer before the client's Finished. More early data than the ticket allows is unexpected_message
- `tls::keysched::early_secret` and `binder_key` (the early secret of a PSK, its "res binder" key)
- TLS OCSP stapling (RFC 6066 8, RFC 8446 4.4.2.1): `ServerConfig::ocsp` (`tls::Staples`: the responses for the certificates a server shows, each checked against its certificate and an issuer that signed it when it is set; one past its nextUpdate, or the end of its delegated responder's certificate, is no longer sent) staples a response to a client that asks for one (status_request). A client asks with `Trust::Anchors`, `System` and `Custom` (`ClientConfig::revocation`, `tls::Revocation`): `Stapled`, the default, checks a stapled response with `x509::ocsp::check` (the issuer from the chain or the anchors) and refuses a certificate it calls revoked (certificate_revoked), takes one without a usable response unless the certificate must be stapled (RFC 7633); `Required` refuses one without a good response (bad_certificate_status_response); `Off` asks for none. TLS 1.3 (the leaf's certificate entry) and TLS 1.2 (CertificateStatus). A resumed session takes the status no longer than the response its handshake checked counts, and a client that checks never resumes a session of `Revocation::Off` (the revocation check is part of `Sessions`' key). `TlsStream::ocsp_response`, `Conn::ocsp_response`. A certificate entry with an extension the other side did not ask for is unsupported_extension (RFC 8446 4.4.2)
- `ocsp::fetch(&client, &cert, &issuer)`: a certificate's status from its CA's OCSP responder (a POST to the first http(s) URI of its authority information access, RFC 6960 A.1; the answer checked); `ocsp::refresh(&staples, &client, &chain, issuer)` keeps a server's staple current (fetched when none is kept or it is halfway through its validity) and says when to call again
- `acme`: certificates from a CA that speaks ACME (RFC 8555: Let's Encrypt, ZeroSSL, Google Trust Services, step-ca). `Acme::new(client, directory)`, `acme.account(key, &NewAccount)` (contact, terms, onlyReturnExisting, external account binding with HS256), `account.issue(&ids, &cert_key, &mut solver, &OrderOptions)`: the order, each authorization proved by a `Solver`, the certificate request, the chain (checked to be for the certificate key and every identifier). Step by step: `new_order`, `authorization`, `respond`, `wait_authorization`, `finalize`, `wait_order`, `certificate` (alternate chains too). Challenges: `Http01` (a handler for /.well-known/acme-challenge/ in a netio `Server`), `TlsAlpn01` (RFC 8737: `setup` makes a `tls::ServerConfig` show the challenge certificate to a client that offers only "acme-tls/1", one challenge per name at a time (the same one twice shares it); a TLS server counts "acme-tls/1" among its protocols only for such a client, so one without protocols of its own still answers the others without ALPN), dns-01 by a solver of the program's (`dns01_name`, `dns01_value`), `Solvers` for several. DNS names, wildcards (dns-01) and IP addresses (RFC 8738); renewal information (ARI, RFC 9773: `Acme::renewal_info`, `ari_id`, `OrderOptions::replaces`), profiles, must-staple; `Account::revoke`, `revoke_with_key`, `change_key`, `update_contact`, `deactivate`. Account keys ES256, ES384, RS256, EdDSA (not every CA takes EdDSA: Let's Encrypt and Pebble do not); every request a JWS with a fresh nonce (badNonce tried again with the nonce of that answer), every URL of the CA https (relative Location and Link headers resolved as RFC 3986 does), answers bounded, waits following Retry-After (the finalize answer's too) up to `Acme::timeout_ms` (no look after it)
- roots: `verify_system_roots(chain, host, roots, now)`, the system's checks against only these CAs (tests of them: `tools/limbo_check.py --system`); `reload()` (the bundle read again at the next check, after setting `SSL_CERT_FILE`, say); `roots::Reason`, `roots::Refused` (plat's)
- HTTP client (security plan 2e): Content-Encoding decoded as the body arrives (gzip, br, zstd with a window of up to 8 MiB as RFC 9659 allows, deflate as zlib; `Client::decode`, on by default: a request without the caller's Accept-Encoding or Range offers "gzip, br", Content-Encoding and Content-Length then leave the answer's headers, `max_body` holds for the decoded body too, `HttpError::Encoding`); redirects (`Client::redirects` / `with_redirects(n)`, off by default: 301, 302, 303, 307, 308 with a Location resolved by `Url::join`; https to http refused; 303, and 301 / 302 after POST, go on as GET without the body and its headers; Authorization, Cookie, Proxy-Authorization and Host stay behind on another origin; `with_redirect_check(f)`; `Client::fetch` -> `Fetched { url, response }`; `HttpError::Redirect`); cookies (`with_cookies(Arc<Mutex<netpkt::cookie::Jar>>)`: the Set-Cookie of every answer stored, redirects included, the jar's cookies sent where the caller set no Cookie header); a connection pool (`with_pool(Pool::new())`, `Pool::with_limits(per_host, max_idle, idle_ms)`: connections kept per origin, proxy and TLS layer, a kept one looked at before use, a GET sent once more on a new connection when a kept one ends before its answer); HTTP proxies (`netio::proxy`: `Proxy::new(url)` with user:password, a proxy per scheme, `no_proxy(list)` with names, addresses and CIDR ranges, `Proxy::from_env()` with http_proxy in lower case only (httpoxy), https_proxy / HTTPS_PROXY, all_proxy and no_proxy as curl reads them; http in absolute form, https through a CONNECT tunnel, `HttpError::Proxy(status)`; loopback and localhost go direct); `Client::deadline_ms` (a whole request, redirects included); `Client::request_on(stream, ..)` (one request over a connection the caller opened); `Url::join` (RFC 3986 5.2, by netpkt::uri), `same_origin`, `authority`, `path`

### Changed

- TLS: a Certificate message may hold 20 certificates (10 before), and an intermediate in it that cannot be read is left out instead of failing the handshake, as browsers do; the peer's own certificate must still be readable
- TLS 1.2: a server without the extended master secret is taken again (since the review of 2026-10-23 it was refused, and with it the TLS 1.2 servers of badssl.com and other old servers). The Triple Handshake attack the extension closes needs session resumption or renegotiation, which netio's client does neither of; resumption, once it comes, will require it
- `x509::Cert::ips` and `CertBuilder::ips` are `x509::IpAddr` (the same shape as `plat::net::IpAddr`; `IpAddr::from([u8; 4])` / `from([u8; 16])`, `from_octets`, `octets` convert); `netio::x509` and `netio::der` are the crate jflib-x509
- (breaking) TLS: `tls::Identity::key` is an `x509::PrivateKey` (`Identity::new(chain, keypair)`, or `keypair.into()`); `tls::ClientConfig` and `tls::ServerConfig` have new fields, built as `ClientConfig { identity: Some(id), ..ClientConfig::new(trust, "host") }` and `ServerConfig { client_auth: Some(trust), ..ServerConfig::new(identity) }`; `tls::keysched` takes the suite's hash and secrets of its length (`Schedule::new(hash, psk, shared)`, `Transcript`)
- TLS: connections that do not trust the system's CAs (`Trust::Anchors`, `Pinned`, `Any`) offer the TLS 1.3 suites, groups and signature schemes of web connections (they stay TLS 1.3 only, without the TLS 1.2 fallback); before they offered ChaCha20-Poly1305, X25519 and Ed25519 only, and two JFLib programs now agree on X25519MLKEM768
- (breaking) TLS: `tls::ClientConfig` has the field `sessions`, `tls::ServerConfig` the fields `tickets` and `early_data`; a config built with `..ClientConfig::new(..)` / `..ServerConfig::new(..)` keeps compiling and resumes nothing
- https resumes its sessions: `trust::system_connector` and `trust::connector` with `ServerTrust::Ca` keep the tickets of the servers they reach (a pin and `Ask` check every handshake's CA and do not resume)
- TLS server: a ClientHello with pre_shared_key but no psk_key_exchange_modes is refused with missing_extension (RFC 8446 4.2.9, 9.2), and one with pre_shared_key may leave out signature_algorithms when its PSK is taken (9.2). TLS client: a NewSessionTicket during TLS 1.2 is unexpected_message (one comes only to a client that asked for tickets), a TLS 1.3 ticket with an extension that does not belong in it illegal_parameter, an empty one decode_error
- TLS clients with `Trust::Anchors`, `System` and `Custom` ask for a stapled OCSP response by default and refuse a certificate a usable response calls revoked; `ClientConfig { revocation: Revocation::Off, .. }` keeps the earlier behaviour. `ClientConfig::revocation` and `ServerConfig::ocsp` are new fields (a config built with `..ClientConfig::new(..)` / `..ServerConfig::new(..)` keeps compiling)
- roots: `verify_system(chain, host, extra, ocsp, now)` answers `Result<(), roots::Refused>` (the system's reason and words, `roots::Reason`) and hands the system the extra CAs and the stapled OCSP response (which it does not check itself: the TLS client does in `check_staple`, another caller with `x509::ocsp::check`); after the system's yes netio checks the leaf once more (`x509::check_leaf`: its name -- no subject CN, IP addresses and the trailing dot as on Linux --, its usage, no CA's extensions on it, no unknown critical one; and a key netio takes), so a system that takes a CA's certificate, keyCertSign or name constraints in a leaf says the same as Linux. `Trust::System`: the TLS alert follows the reason (certificate_expired, certificate_revoked, bad_certificate for another name, unsupported_certificate for another usage, unknown_ca); with TLS 1.2 the chain is checked at the ServerKeyExchange, after a stapled response that may come between, so the system reads it as well. `system_anchors` reads the bundle again when it changed (looked at once a minute at most)
- netio takes JSON from `formats::json` instead of `agent_core::json` (the same module; netio no longer depends on jflib-agent-core)
- `Url::parse` checks the host: a name of letters, digits and - . _ ~ (an IDN as its A-label), a dotted IPv4 address, or an IPv6 literal in brackets (with a zone as RFC 6874 writes it). A name that ends in a number must be a dotted IPv4 address, so "0x7f.1", "2130706433" and "127.1", which resolvers in the manner of inet_aton read as 127.0.0.1, are refused. Bytes beyond ASCII and " < > ` { } in the target are percent-encoded, "host:" is the default port, port 0 is refused
- The HTTP client offers gzip and br and decodes them by default (`Client::decode`); `Session` takes its client's proxy, cookies and decoding; headers whose name is not a token or whose value holds a control character (NUL among them; a tab is fine) are not written. netio depends on jflib-compress and jflib-netpkt

### Fixed

- `dns::resolve` (Linux, macOS): a numeric address or `localhost` no longer reads /etc/hosts and /etc/resolv.conf, which an app's rules do not grant on macOS (PERMDENY lines for every WebSocket and HTTP connection to an address).
- SSH: a peer that sends only messages to skip (ignore, debug, banners, global requests) while an answer is due ends the session after 1024 of them (login and opening a channel never returned); data past the channel window the client granted is a protocol error.
- TLS: a plaintext alert during the handshake ends the connection like an encrypted one (it was answered with unexpected_message); a Finished of the wrong length is answered with decode_error instead of decrypt_error (RFC 8446 4.4.4)
- TLS server, as tlsfuzzer checks RFC 8446: an empty alert record is answered with unexpected_message, a record that holds only padding (no content type) with unexpected_message instead of bad_record_mac, a protected record over 2^14 + 1 bytes of inner plaintext (padding included) or a plaintext record over 2^14 with record_overflow; a ClientHello with supported_groups but no key_share with missing_extension, one with a legacy_version below 0x0303 with protocol_version; a second dummy change_cipher_spec, or one before the first ClientHello, with unexpected_message; a second ClientHello that differs from the first in more than key_share, cookie, early_data and padding with illegal_parameter (as does early_data in it); and 0-RTT data the server does not take is skipped as RFC 8446 4.2.10 asks (at least 64 KiB of it) instead of ending the handshake; application data or a change_cipher_spec between the parts of a handshake message split over records with unexpected_message (RFC 8446 5.1; application data inside a KeyUpdate was delivered); an empty application_data record counts as 0-RTT data only when the client offered early data (one between the parts of a ClientHello was skipped and the handshake waited), and after a HelloRetryRequest nothing is skipped once the second ClientHello came (a record that does not open is bad_record_mac); a pre_shared_key that is not the last extension with illegal_parameter (RFC 8446 4.2.11)
- TLS server: a second ClientHello whose pre_shared_key has new binders or ticket ages, as RFC 8446 4.1.2 allows, is taken; it was refused with illegal_parameter, which ended the handshake of a client that holds a ticket (from an earlier server under the same name) after a HelloRetryRequest
- TLS client: an extension in the ServerHello or EncryptedExtensions that the ClientHello did not offer (an unknown type, a GREASE value) is refused with unsupported_extension, one it offered in a message that does not answer it with illegal_parameter (RFC 8446 4.2, RFC 5246 7.4.1.4, RFC 8701 4; `tls::conn::AL_UNSUPPORTED_EXTENSION`). They were ignored; TLS-Anvil found it
- TLS, as TLS-Anvil checks the client: a TLS 1.2 peer's close_notify is answered with one (RFC 5246 7.2.1); an empty handshake record, protected or not, is unexpected_message (RFC 8446 5.1; a protected one was taken, a plaintext one was decode_error); the client ignores a TLS 1.3 ServerHello's legacy_version (RFC 8446 4.2.1; anything but 0x0303 was protocol_version) and refuses one older than TLS 1.2 only without supported_versions
- `dns::resolve` on macOS and iOS asks the system's resolver (`getaddrinfo`, as `plat::net::resolve` does there) instead of reading /etc/hosts and /etc/resolv.conf: names behind a VPN with name servers of its own (split DNS), `.local` over mDNS and the rules of iOS resolve, and a sandboxed Mac app, which may not read those files, resolves names at all; the app's net.connect rules apply as before
- `dns::resolve` (the own resolver, Linux and `resolve_with`): an answer with "no such name" (NXDOMAIN) counts only when it carries the query's question, like every other answer (it was taken before the question was compared, so one with the right id and another question could make a name not found); names in answers are compared label by label (a dot or backslash inside a label is escaped, a byte outside printable ASCII is \DDD as in RFC 1035 5.1), so a record whose owner is one label "www.example.com" no longer counts for the name www.example.com
- `dns::resolve` and `resolve_with` answer a name under .localhost written absolute (`app.localhost.`, `localhost.`) with the loopback addresses as well: it went to /etc/hosts and the name servers (RFC 6761 6.3). And a net.connect rule of such a name (`app.localhost:8080`) now covers the loopback addresses of the answer, which were not registered with the app's rules, so a connection to them was Denied
- HTTP server: a connection the client ends (its close_notify over TLS, or a closed socket) is ended with the server's close_notify, as RFC 8446 6.1 asks; before the server only closed the socket (TLS-Anvil AlertProtocol.sendsCloseNotify)
- TLS: a handshake message longer than a record (a certificate chain of over 16 KiB) goes in several records (RFC 8446 5.1); it went in one record, which the peer refused (record_overflow)

### Security

- `ssh`: `private_key` overwrites the key file's decoded bytes and text, `auth_password` the message with the password, once used.
- `x509::Cert::verify` reads an ECDSA signature (certificates, TLS CertificateVerify) strictly as DER: nothing after the SEQUENCE or in it after s, r and s in the shortest form of a non-negative INTEGER. Bytes appended to the signature and zeros put before r or s were accepted, so a CA-signed certificate could be re-encoded into copies with other fingerprints that still validated (no forgery; Wycheproof's InvalidEncoding cases, tools/wycheproof_check.py now without a failure)
- TLS refuses handshake data that crosses any change of the read key (RFC 8446 5.1): the application keys after Finished and those of a KeyUpdate count too; before, only the first keys did
- X.509 closes what x509-limbo found: name constraints are processed for e-mail addresses, URIs (their host) and directory names too, and a constrained form netio does not process refuses the certificates below it (such constraints were dropped); they apply to the intermediates below a CA as well, not only to the leaf. Refused now: RSA keys under 2048 bits or not in whole bytes, an unknown critical extension in a trust anchor, an empty extended key usage, a subject alternative name that is empty, of an unknown form, an iPAddress of another length or a dNSName outside the preferred name syntax (an underscore, a leading dot), NameConstraints without subtrees, critical AKI / SKI, name constraints or keyCertSign in a leaf without cA, a CA with an empty subject. Self-issued intermediates no longer count against pathLenConstraint
- DNS: an answer counts only with addresses of the asked name, or of the name its CNAME chain in the answer leads to (at most 8 steps); records for other names in an answer were taken as well
- PEM (`pem::decode_all`) is read line by line, each line compared with the markers, instead of with a substring search across the text, whose steps depended on which Base64 characters a private key has (tools/ct_check.py's memcheck found it); a marker must stand on a line of its own (RFC 7468)
- TLS: the secrets of the key schedule are wiped when a connection is dropped, and a traffic secret when KeyUpdate replaces it (also the copies a handshake made of them); a hybrid key exchange wipes its ECDH secret when the ML-KEM half is refused
- `Trust::System(extra)`: the system checks the extra CAs (a company CA) under its own policy -- Windows CryptoAPI with them as its only roots where its own give no path, Apple's Security framework with them as anchors beside its own -- and its answer stands; on Linux they count where the bundle gives no path to a CA. A chain the system refused for another reason -- a certificate it knows to be revoked or a key it distrusts, an expired one, one for another name or purpose, one without the Certificate Transparency Apple asks of public roots -- stays refused; before, netio's own check took it when it also led to one of the extra CAs (a company CA the system trusts as well)
- HTTP client and `Session`: an answer without Content-Length or Transfer-Encoding on a kept-alive connection was read as empty, and its body became the next answer (response desync); it now runs to the end of the connection, which then closes (RFC 9112 6.3). A connection carries another request only after a body of known length read to its end with no byte after it, without Connection: close, not after HTTP/1.0 without keep-alive and not after an answer with both Transfer-Encoding and Content-Length. The status line needs three digits from 100 to 599 ("+200" and "20" were taken); at most 16 interim answers come before the final one (an endless 100 Continue held the client as long as the server liked), an unasked 101 is refused; `http::Reader` takes Transfer-Encoding only as exactly "chunked" over all its header lines (a second line was not looked at), for a server's requests too

## [0.2.1] - 2026-11-16

### Added

- `Stream::end_is_clean()` (default true): after a read gave 0, whether the peer ended the stream in order. `TlsStream` answers whether close_notify came.
- `x509::CertBuilder::sign_ext` (further extensions; one with the OID of a built-in one replaces it) and `x509::extension`; `server::MIN_BODY_RATE` and `http::Reader::set_min_rate`

### Fixed

- Server: a request body sent a byte at a time (each within `read_ms`) held a worker as long as the client liked; a body must now bring `MIN_BODY_RATE` (1 KiB a second) on average after a first `read_ms`, else the connection ends
- TLS: records that carry no data (empty application data records) kept `TlsStream::read` going without end, past the read timeout and the HTTP deadlines, which are checked between reads; a read now ends with TimedOut after the stream's read timeout without data
- X.509: a wildcard certificate (`*.example.com`) passed a CA's excluded name constraint for a host it stands for (`secret.example.com`) or for the subdomains of its base (`.example.com`); and the extended key usage of the CAs on the path was not checked, so a CA for client certificates (also a trusted one) could certify a server

### Security

- A response without a length, which runs to the end of the connection, ends only at an orderly end. A reset, or a TLS connection closed without close_notify, is an error instead of the whole body.
- SSH `exec`: the names of `exit-signal` requests count against `max_out` like the output.

## [0.2.0] - 2026-11-14

### Fixed

- `Client::new()` sends the user agent `JFLib-netio` and `ssh::Client` the version `SSH-2.0-JFLib_netio` (both still named CraftLIB); a mail without a HELO name gets its Message-ID at `jflib` instead of `backupcraft`
- `smtp::send` with `Security::None`: the docs (GUIDE section 17, the README) say what the code does, a plain connection to any server (a relay on port 25 inside a network) and no login without TLS; they said "plain on loopback"
